# Progress 4 — สรุปผลการทดลองโมเดล LightGBM

* **โมเดล:** LightGBM (`LGBMClassifier`)
* **เป้าหมาย:** จำแนกประเภทการโจมตีทางไซเบอร์ 10 คลาส (Normal + 9 รูปแบบการโจมตี) บนชุดข้อมูล UNSW-NB15
* **การแบ่งข้อมูล:** Temporal Split (70% Train / 10% Val / 20% Test ตามลำดับเวลาจริง)
* **เมทริกซ์หลัก:** Macro F1-Score, PR-AUC, Macro Recall

## 1. ผลการปรับจูน Hyperparameter บนชุด Val (10 Trials)

จากการทดลองปรับจูนค่าพารามิเตอร์ 10 รูปแบบ เพื่อรับมือกับปัญหา Class Imbalance ขั้นรุนแรง (Normal 1.39 ล้านแถว vs Worms 88 แถวใน Train) และลดการครอบงำของฟีเจอร์เดี่ยว (`smeansz`) ได้ผลลัพธ์บนชุด Val ดังนี้:

| ลำดับ (Trial) | จุดเด่นของพารามิเตอร์ | Val Macro F1 | Val PR-AUC | Val Recall | ผลการวิเคราะห์ |
| :---: | :--- | :---: | :---: | :---: | :--- |
| **1** | `class_weight=None` | 0.3322 | 0.2458 | 0.3304 | **ล้มเหลว** โมเดลละเลยคลาสหายากแล้วทายแต่ Normal |
| **2** | `class_weight='balanced'` | 0.6103 | 0.6185 | 0.7393 | **คะแนนพุ่งขึ้นเท่าตัว** ยืนยันว่าการถ่วงน้ำหนักคลาสจำเป็นอย่างยิ่ง |
| **3** | `lr=0.05, n_estimators=150` | 0.6101 | 0.6304 | 0.7474 | ปรับ step ละเอียดขึ้น ช่วยให้ PR-AUC และ Recall ขยับขึ้น |
| **4** | `num_leaves=63` | 0.6167 | 0.6375 | 0.7256 | เพิ่มความลึกของใบไม้ ช่วยจับ Pattern การโจมตีที่ซับซ้อน |
| **5** | `colsample=0.8, min_child=50` | 0.6233 | 0.6463 | 0.7438 | สุ่มฟีเจอร์ 80% บังคับให้ต้นไม้เรียนรู้สัญญาณรอง |

| **8** | `reg_alpha=0.1, reg_lambda=1.0` | 0.6215 | 0.6436 | 0.7461 | ใส่ Regularization L1/L2 ช่วยคุมไม่ให้ Overfit |
| **9** | `max_depth=8, num_leaves=45` | 0.6066 | 0.6335 | **0.7575** | คุมความลึกไม่เกิน 8 ชั้น Recall พุ่งสูงสุด แต่ Precision ตก |
| **10** | `max_depth=10, num_leaves=95` | 0.6139 | 0.6385 | 0.7501 | ต้นไม้ใหญ่เกินไป เริ่มจำ Noise ทำให้ Macro F1 ลดลง |

## 2. การวัดผลไฟนอลบนชุด Test (Final Evaluation)

นำ Best Model (Trial 6) ไปประเมินผลบนชุด **Test** (ข้อมูลในอนาคต 20% สุดท้าย) เพียงครั้งเดียวตามกฎของทีม:

| ชุดข้อมูล | Macro F1 | PR-AUC | Macro Recall | การเปลี่ยนแปลง |
| :--- | :---: | :---: | :---: | :---: |
| **Validation (10%)** | **0.6245** | **0.6384** | **0.7501** | *Baseline จูน* |
| **Test (20%)** | **0.6059** | **0.6149** | **0.7267** | *-0.0186 (เสถียรมาก)* |

> **ข้อสังเกต:** คะแนนบนชุด Test ดรอปลงจาก Val เพียงเล็กน้อย (~0.018) แม้ว่าข้อมูลจะถูกแบ่งตามเวลาจริง (Temporal Split) ซึ่งมีสภาวะ Data Drift แสดงว่าโมเดลไม่มีอาการ Overfitting และสามารถ Generalize สู่ข้อมูลในอนาคตได้อย่างยอดเยี่ยม

## 3. การทดลองเปรียบเทียบ 3 มิติ (Base vs Base+Geo vs Base+TTL)

การทดลองควบคุมตัวแปรเพื่อตอบ 2 คำถามวิจัยหลักของโปรเจกต์:
1. การเพิ่ม Geolocation (ประเทศ & ASN) ช่วยเพิ่มความแม่นยำหรือไม่?
2. ฟีเจอร์กลุ่ม TTL เกิด Data Leakage จริงหรือไม่?

| โมเดล | ฟีเจอร์ที่ใช้ | Test Macro F1 | Test PR-AUC | Test Recall | ผลการเปรียบเทียบ |
| :--- | :--- | :---: | :---: | :---: | :--- |
| **Base (`lgbm`)** | 38 ฟีเจอร์พื้นฐาน | **0.6059** | 0.6149 | **0.7267** | **โมเดลหลักที่ปลอดภัยและใช้งานได้จริง** |
| **Base + Geo (`lgbm_geo`)** | Base + 4 Geo (Flags & Top-50) | **0.6051** | **0.6156** | **0.7251** | **PR-AUC สูงสุด (+0.0007)** ช่วยจัดอันดับความเสี่ยงดีขึ้น |
| **Base + TTL (`lgbm_ttl`)** | Base + 3 ฟีเจอร์ TTL | **0.6183** | **0.6323** | **0.7408** | **คะแนนพุ่งสูงผิดปกติ** (หลักฐานยืนยัน Leakage) |

### บทวิเคราะห์ผล Geolocation (`lgbm_geo`)
* **เห็นอะไร:** ในรอบแรกที่ใส่ Raw Geo (`src_country`, `dst_country`, `src_asn`, `dst_asn`) คะแนน F1 ตกเหลือ 0.6013 แต่หลังจากทำการ **Feature Engineering** (สร้าง Flags: `is_private_src`, `is_private_dst`, `is_same_country` และยุบกลุ่ม ASN หางยาวเหลือ Top-50) คะแนน Test F1 พุ่งกลับขึ้นมาเป็น **0.6051** และ **PR-AUC ขยับแซง Base ขึ้นไปอยู่ที่ 0.6156**
* **สรุป:** ข้อมูล Geolocation ช่วยให้โมเดลประเมินความน่าจะเป็นของความเสี่ยง (PR-AUC) ได้ดีขึ้น แต่ต้องระวังปัญหา Temporal Shift ของเลข ASN ในโลกจริง

### บทวิเคราะห์ผล TTL Leakage (`lgbm_ttl`)
* **เห็นอะไร:** เมื่อใส่ฟีเจอร์ TTL (`sttl`, `dttl`, `ct_state_ttl`) คะแนนพุ่งขึ้นชัดเจนทั้ง Val และ Test (F1 ทะลุ 0.6183, Recall แตะ 0.7408)
* **สรุป:** ยืนยันข้อสันนิษฐานจาก EDA ว่า **TTL ใน UNSW-NB15 เป็น Data Leakage** ที่เกิดจากการตั้งค่าในห้องทดลอง (Lab Artifact) การตัด TTL ออกในการเทรนโมเดลหลักถือเป็นการตัดสินใจที่ถูกต้องตามจรรยาบรรณวิจัย

* **อันดับ 1:** **`smeansz` (Mean Packet Size ฝั่งต้นทาง)** มีความสำคัญสูงที่สุดแบบขาดลอย (>11,000) แสดงว่าขนาดเฉลี่ยของแพ็กเก็ตต้นทางคือตัวบ่งชี้ทราฟฟิกการโจมตีที่ทรงพลังที่สุด

## 5. สรุปภาพรวมและข้อเสนอแนะ (Conclusion)

1. **โมเดลที่แนะนำให้เลือกใช้:** **Base LightGBM (Trial 6)** หรือ **LightGBM + Engineered Geo**
   * ได้คะแนน **Macro F1 = 0.6059**, **PR-AUC = 0.6149**, และ **Recall สูงถึง 0.7267**
   * ไม่มีปัญหา Data Leakage และพร้อมรับมือกับข้อมูลทราฟฟิกในอนาคตได้อย่างมั่นใจ
2. **บทเรียนสำคัญด้าน Data Science:**
   * **Class Imbalance:** การใช้ `class_weight='balanced'` คือหัวใจสำคัญที่สุดที่กู้คะแนน Macro F1 จาก 0.33 ขึ้นมาแตะ 0.61
   * **Subsampling:** การสุ่มใช้ฟีเจอร์ 75% (`colsample_bytree: 0.75`) ช่วยลดการครอบงำของฟีเจอร์มหาอำนาจอย่าง `smeansz` และผลักดันให้โมเดลมี Recall สูงขึ้นในทุกคลาส
   * **Geo Engineering:** การนำข้อมูล Geo มาใช้จริงใน Time-series ต้องทำการลด Noise (ยุบ Top-K ASN) และแปลงเป็น Status Flags ถึงจะได้ประโยชน์สูงสุด

## 6. บทวิเคราะห์เชิงลึก: ทำไม `colsample_bytree: 0.75` และ `min_child_samples: 50` ถึงเป็น Optimal Sweet Spot?

จากการวิเคราะห์พฤติกรรมของโมเดลต่อข้อมูลที่มีความไม่สมดุลขั้นรุนแรง (Worms มี 88 แถว vs Normal 1.39 ล้านแถวใน Train) การปรับค่าตัวแปรทั้งสองตัวนี้อย่างสุดโต่งจะส่งผลเสียอย่างชัดเจน:

### 1) หากลด `colsample_bytree` ต่ำลงไปอีก (< 0.70 เช่น 0.50 หรือ 0.40)
* **ปัญหา Underfitting (ต้นไม้อ่อนแอเกินไป):** จากฟีเจอร์ทั้งหมด 38 ตัว หากสุ่มใช้เพียง 50% (เหลือ 19 ตัว) มีโอกาสสูงมากที่ต้นไม้บางต้นจะ **ขาดฟีเจอร์หลักในการตัดสินใจไปพร้อมๆ กัน** เช่น ไม่ได้ทั้ง `smeansz`, `sbytes`, และ `stcpb`
* **ผลกระทบ:** คลาสที่มี Signature จำเพาะ (เช่น DoS ที่ต้องดู Packet Rate ร่วมกับ Byte Size) จะไม่สามารถแยกแยะได้ ทำให้ทั้ง Precision และ Macro F1 ร่วงลง (สังเกตได้จาก Trial ที่ใช้ 0.70 คะแนนเริ่มดรอปลงเมื่อเทียบกับ 0.75)

### 2) หากเพิ่ม `min_child_samples` สูงขึ้นไปอีก (> 80 เช่น 100 หรือ 150)
* **ความเสี่ยงขั้นวิกฤตต่อคลาส Worms (มีแค่ 88 แถว):**
  * เกณฑ์ `min_child_samples` คือจำนวนตัวอย่างขั้นต่ำที่ใบไม้ (Leaf) ต้องมีจึงจะยอมแตกกิ่งได้
  * หากตั้งค่าเกิน 88 (เช่น 100): **ต้นไม้จะไม่สามารถสร้างใบไม้เพื่อทายผลว่าเป็น "Worms" ได้เลยแม้แต่ใบเดียว** เพราะจำนวนแถวในชุด Train ไม่ผ่านเกณฑ์ขั้นต่ำ
  * Worms จะถูกบังคับให้ไปรวมกลุ่มกับคลาสอื่น (เช่น ถูกกลืนไปอยู่กับ Exploits หรือ Normal)
* **ผลกระทบ:** Recall ของคลาส Worms จะดิ่งลงเหลือ 0 ทันที และเนื่องจากใช้ Macro F1 ซึ่งให้น้ำหนักทุกคลาสเท่ากัน คะแนนภาพรวมจะพังทลายอย่างรุนแรง

### 3) หากลด `min_child_samples` ต่ำลงไปอีก (< 20 เช่น 5 หรือ 10)
* **ปัญหา Severe Overfitting (จำข้อสอบ):**
  * ต้นไม้จะแตกกิ่งย่อยลึกเกินไปจนไป "จำ Noise" หรือลักษณะเฉพาะของทราฟฟิกเพียงไม่กี่แถวในอดีต
* **ผลกระทบ:** คะแนนบนชุด Train จะสูงเกือบ 100% แต่เมื่อนำไปทดสอบบนชุด Test ซึ่งเป็นข้อมูลทราฟฟิกในอนาคต คะแนนจะร่วงลงทันที

### ตารางสรุป Trade-off Matrix

| พารามิเตอร์ | ปรับต่ำเกินไป | ค่าที่เหมาะสมที่สุด (Trial 6) | ปรับสูงเกินไป |
| :--- | :--- | :---: | :--- |
| **`colsample_bytree`** | **< 0.70:** ต้นไม้ขาดฟีเจอร์หลัก เกิด Underfitting | **0.75:** กระจายการเรียนรู้ดีที่สุด ไม่พึ่งพา `smeansz` ตัวเดียว | **1.00:** ฟีเจอร์ `smeansz` ครอบงำโมเดล บดบังฟีเจอร์อื่น |
| **`min_child_samples`** | **< 20:** โมเดลแตกกิ่งลึกไปจำ Noise (Overfit) | **50:** กรอง Noise ได้ดี และคลาส Worms (88 แถว) ยังแตกกิ่งได้สมบูรณ์ | **> 80:** **กลืนคลาส Worms หายไป** Recall ของ Worms กลายเป็น 0 ทันที |
